The service we are building

A command-line program reads a JSON file, validates it, downloads a finite batch of random JPEG photos from Picsum, saves them to a configured directory, and reports success or failure. “Service” means a reusable application component here; running continuously or exposing an HTTP API is a later project.

  • Configuration: JSON first, because Foundation provides decoding without a YAML dependency. A checked-in example supplies safe defaults; a command-line path selects the actual file. Relative output paths resolve against the configuration file's directory.
  • Injection: construct dependencies explicitly at the entry point. Pass configuration values and protocol implementations through initializers. No DI framework is needed.
  • Concurrency: learn a single async download first, then bounded task groups, safe shared state, and cooperative cancellation.
  • Failure policy: initially fail the batch on the first error. Cancel remaining work, keep files already committed successfully, and report partial progress. Cancellation never triggers a retry. We will document races with already-finishing operations rather than promise rollback.
  • Limits: validate batch count, dimensions, concurrency, timeout, and maximum accepted response size. The first in-memory transport is educational; its post-download size check is not a hard network-memory limit. Lesson 14 addresses that limitation.
  • Testing: cover all owned decisions and failure paths. Coverage numbers help find gaps; they do not prove correctness or require testing Foundation internals.

Picsum documents size-based random images, JPEG suffixes, and a random query parameter for avoiding cached repeats. That parameter does not guarantee unique photos. See the Picsum API examples.

Architecture we will grow into

CLI / composition root
  ├── JSON loader → validated configuration
  └── DownloadCoordinator
        └── PhotoDownloader
              ├── PhotoSource ← PicsumPhotoSource
              ├── HTTPClient  ← URLSessionHTTPClient
              └── PhotoStore  ← DiskPhotoStore

Tests inject controlled fakes at the same boundaries.

Arrows describe dependency relationships, not threads. Protocols describe capabilities the application needs; adapters translate networking and filesystem APIs into those capabilities. The coordinator schedules work; the downloader handles one photo. The entry point knows concrete types so the application logic does not have to.

Keep one executable module initially. Folders communicate responsibilities without prematurely adding packages or targets. Introduce a library target only when reuse or testing constraints justify it. Use structs for immutable values and actors when mutable state genuinely crosses tasks.

Load configuration at the edge

What and why: the program reads configuration once. Business logic receives values, not a filename or a global singleton. Inject a small reading function to test missing files without touching disk.

Files: create Configuration/ConfigurationLoader.swift and ConfigurationLoaderTests.swift. Keep argument parsing for lesson 9.

struct ConfigurationLoader {
    let read: (URL) throws -> Data

    func load(from url: URL) throws -> DownloadConfiguration {
        let bytes = try read(url)
        let raw = try JSONDecoder().decode(RawConfiguration.self, from: bytes)
        return try DownloadConfiguration(
            raw: raw, relativeTo: url.deletingLastPathComponent()
        )
    }
}
// In a test: ConfigurationLoader(read: { _ in fixtureData })

Your exercise: import Foundation, connect decoding to validation, and add useful context to file/decoding errors without hiding the original cause. Compare closure injection here with protocol injection in the next lesson.

08 · 60 minutes · 10 explain / 25 implement / 20 test / 5 PR

Persist complete files safely

What and why: filenames, directory creation, overwrite policy, and partial files are storage concerns. Use a unique directory per run and deterministic names within it to prevent collisions across invocations.

Files: create Infrastructure/DiskPhotoStore.swift and DiskPhotoStoreTests.swift. Keep the store responsible for its root directory; use injected roots in tests.

actor DiskPhotoStore: PhotoStore {
    let directory: URL
    // Exercise: initializer and directory setup.

    func save(_ data: Data, named name: String) async throws -> URL {
        // Validate a simple leaf name; reject paths and traversal.
        let destination = directory.appendingPathComponent(name)
        try data.write(to: destination, options: .atomic)
        return destination
    }
}

Your exercise: complete safe leaf-name validation and the no-overwrite policy within a unique run directory. Atomic writing avoids exposing partially written files; it does not by itself enforce no-overwrite or guarantee durability after power loss. Actor isolation protects state, but synchronous disk writes still block the executing thread; keep this initial version limited to small images.

Tests / PR: use unique temporary directories with cleanup. Verify saved bytes, missing directory creation, invalid names, duplicates, and a deterministic failure such as using a file as a parent directory. These are local filesystem integration tests; downloader unit tests continue using fakes. PR: lesson-08-disk-storage.

Understand isolation before adding tasks

What and why: learn which values may cross task boundaries and where mutable state lives. Discuss actor reentrancy: an actor can process another operation while one method is suspended.

Files: review existing source types for sendability; create TestDoubles/ConcurrencyProbe.swift and ConcurrencyProbeTests.swift.

actor ConcurrencyProbe {
    private(set) var active = 0
    private(set) var peak = 0

    func started() {
        active += 1
        peak = max(peak, active)
    }
    func finished() { active -= 1 }
}

Your exercise: deliberately inspect one unsafe shared-mutation example in a scratch discussion, then explain the compiler's objection. Keep the final code safe. Examine how the package's actual concurrency setting affects isolation instead of changing settings or adding @unchecked Sendable to make errors disappear.

Tests / PR: verify probe accounting and actor access with await. Each test owns its own probe; no shared global recordings. PR: lesson-10-isolation.

Run a bounded number of downloads

What and why: a task per photo starts too much work for large batches. A sliding window starts at most the configured limit, replacing one task whenever a result completes.

Files: create Services/DownloadCoordinator.swift, DownloadCoordinatorTests.swift, and a gated test downloader; replace the sequential loop in DownloadApplication.swift.

    while let result = try await group.next() {

        // Submit one next request if any remain.

Your exercise: use a @Sendable async throwing operation closure to inject one-photo work into the coordinator. Keep scheduling independent of networking. Explain why completion order differs from input order and why an actor for the parent-owned result array is unnecessary.

Tests / PR: use actor-controlled gates, not sleeps, to prove peak work never exceeds the limit and that concurrency actually reaches two when permitted. 12 · 60 minutes · 15 explain / 20 implement / 20 test / 5 PR

Make cancellation and partial failure explicit

What and why: cancellation is cooperative. A throwing task group cancels children when an error escapes its body, but waits for them to finish. Dependencies must cooperate; cancellation is not instant rollback.

Files: update downloader, coordinator, HTTP adapter, their tests, and cancellation-aware test gates. Add Domain/BatchFailure.swift for structured partial outcomes if needed.

try Task.checkCancellation()
let payload = try await http.get(url)
try Task.checkCancellation()
// Validate before attempting persistence.
let savedURL = try await store.save(payload.data, named: name)

Your exercise: check cancellation before submitting replacement tasks and before persistence. Normalize transport cancellation at the application boundary when appropriate. Keep successfully saved files and report them even when another child fails; design result accounting so late successes are not silently lost during cancellation.

Tests / PR: cancellation before start, during an awaited transport, and before save; first-error sibling cancellation; preserved committed files. Use cancellation-aware continuations/gates with exactly-once resume and a bounded test timeout as a deadlock guard. No wall-clock timing assertions. Programmatic task cancellation comes first; cross-platform Ctrl+C signal integration is a separate extension. PR: lesson-12-cancellation.

Reduce memory pressure and own temporary files

What and why: buffering every image as Data scales poorly. A post-response size check rejects oversized content only after buffering it. Explore file-backed URLSession downloads and the available Windows API before selecting the adapter.

Files: evolve HTTPPayload.swift, HTTPClient.swift, transport/retry adapters, and PhotoStore.swift to exchange an owned temporary-file result; update affected fakes and tests. Keep the old adapter until the new contract works.

// Proposed replacement for an in-memory payload:
struct DownloadedFile: Sendable {
    let temporaryURL: URL
    let statusCode: Int
    let contentType: String?
    let byteCount: Int64
}
// Desired ownership rule:
// transport creates → downloader validates → store commits
// downloader removes any uncommitted temporary file on every exit.

Your exercise: confirm the installed Foundation supports the chosen download API. Write down who deletes files on rejected responses, retries, cancellation, and success. File-backed downloads reduce memory use but do not cap disk/network consumption automatically. A strict transfer-byte ceiling requires a delegate/streaming implementation that cancels while receiving data; treat that as a follow-up lesson if it exceeds this session.

Tests / PR: fake temporary files cover successful commit, rejected size, retry cleanup, cancellation, and storage failure. Verify no temporary files remain.
